## 一、技术亮点概览

实现智能上下文压缩中间件，通过 Token 监控自动触发摘要，压缩率 70-85%，显著降低 LLM 成本并避免上下文超限。设计结构化摘要 Prompt，保留会话意图、用户偏好、进度决策等关键信息，确保多轮对话的上下文连贯性。实现 Token 计量中间件，监控精度 ±10%，支持按 Run 统计 Token 用量，为成本核算和性能优化提供数据支撑。

**核心价值**：
- **成本优化**：压缩率 70-85%，成本降低 60-75%
- **上下文安全**：避免 128K+ token 上下文超限导致的对话失败
- **信息保留**：结构化摘要确保关键信息不丢失

**Token 估算方法**：

> ⚠️ 项目实际使用 `langchain_core.messages.utils.count_tokens_approximately` 进行近似计数，以下 `estimate_messages_tokens` 为思路示意，非项目当前代码。

```python
# 项目实际使用 LangChain 的近似计数方法
from langchain_core.messages.utils import count_tokens_approximately

# 优势：无需加载模型，速度快
# 精度：±10%（生产环境验证）
# 劣势：不如 tiktoken 精确

# 以下为简化示意（非项目实际实现）
def estimate_messages_tokens(messages: list) -> int:
    """简化估算思路：中文约 1.5 字/token，英文约 4 字符/token"""
    total = 0
    for msg in messages:
        total += 4  # 基础开销
        content = msg.content if isinstance(msg.content, str) else str(msg.content)
        total += len(content) / 2  # 混合语言粗略估算
    return int(total)
```

```python
def truncate_tool_result(result: str, max_tokens: int = 500) -> str:
    """截断长工具输出，避免工具结果占用过多上下文"""
    if estimate_tokens(result) <= max_tokens:
        return result

    # 存储完整输出
    output_path = save_tool_output(result)

    # 返回预览
    preview = result[: max_tokens * 4]  # 按字符估算
    return f"{preview}\n\n... (完整输出已保存到 {output_path})"
```

### 2.5 权限控制机制

**基于角色的配置过滤**（backend/package/starring/agents/context.py:102-124）：
```python
def filter_config_by_role(
    config_json: dict,
    role: str | None,
    context_schema: type[BaseContext] | None = None,
) -> dict:
    """从 Context 字段 metadata.auth 过滤 config_json.context"""
    if not isinstance(config_json, dict):
        return {}

    schema = context_schema or BaseContext
    restricted_fields = {
        f.name
        for f in fields(schema)
        if f.metadata.get("auth") and not _role_can_access(str(f.metadata.get("auth")), role)
    }

    if not restricted_fields:
        return dict(config_json)

    filtered = dict(config_json)
    context = filtered.get("context")
    if isinstance(context, dict):
        filtered["context"] = {
            key: value for key, value in context.items() if key not in restricted_fields
        }
    return filtered


def _role_can_access(auth: str | None, role: str | None) -> bool:
    """检查角色是否有权限访问"""
    if not auth:
        return True
    if auth == "admin":
        return role in {"admin", "superadmin"}
    if auth == "superadmin":
        return role == "superadmin"
    return False
```

## 五、面试要点

### Q1: 为什么要设计结构化摘要 Prompt？

**参考回答**：
结构化摘要有 3 个核心优势：

1. **信息保留完整**：通过明确分类（会话意图、用户偏好、进度决策、文件引用、后续待办），确保关键信息不丢失
2. **提升后续对话效率**：模型能快速定位历史关键信息，无需重新阅读完整对话
3. **便于人工审查**：结构化输出便于开发者调试和审计对话历史

相比传统的"总结对话历史"，结构化摘要更适合 Agent 场景，因为 Agent 需要知道"下一步该做什么"，而不仅仅是"之前聊了什么"。

### Q2: Token 监控精度为什么是 ±10%？如何提升？

**参考回答**：
±10% 的精度是基于实际生产环境验证的估算值。精度主要受以下因素影响：
1. **语言差异**：中文（1.5 字/token）vs 英文（4 字符/token）
2. **特殊字符**：代码中的符号、空格等
3. **工具调用**：JSON 结构化数据的额外开销

提升精度的方法：

1. **实时获取**：部署 LLM API（如 OpenAI）返回实际 token 数，可以记录并修正估算
2. **分词器对齐**：使用与模型相同的分词器（如 tiktoken）
3. **缓存校准**：记录估算值与实际值的偏差，动态调整估算系数

但在生产环境中，±10% 的精度已经足够支持成本核算和阈值触发，无需过度追求高精度。

### Q3: 如何选择触发阈值和保留消息数？

**参考回答**：
阈值和保留消息数需要根据实际场景权衡：

**触发阈值（默认 100K）**：
- **低阈值（50K）**：适合短对话场景，成本更低，但可能丢失部分历史信息
- **高阈值（150K）**：适合长对话场景，保留更多上下文，但成本更高
- **建议**：根据模型上下文窗口（如 128K）设置在 80-100K，留出安全缓冲

**保留消息数（默认 10）**：
- **少保留（5 条）**：压缩率更高，但可能丢失最近的上下文
- **多保留（20 条）**：保留更多最近上下文，但压缩率降低
- **建议**：根据对话轮次和用户习惯调整，一般 10 条足够

实际项目中，这两个参数应该支持动态配置，并通过 A/B 测试找到最优值。

### Q4: 压缩中间件对系统性能有什么影响？

**参考回答**：
主要影响：
1. **额外延迟**：生成摘要需要调用 LLM，通常增加 1-3s 延迟
   - 优化：使用更快的模型（如 gpt-3.5-turbo）生成摘要
   - 优化：异步处理，不阻塞用户请求
2. **额外成本**：摘要生成需要额外 token 消耗
   - 但相比不压缩的长对话成本，总体成本仍降低 60-75%

3. **准确性风险**：摘要可能遗漏重要信息
   - 缓解：结构化 Prompt 确保关键信息保留
   - 缓解：保留最近 N 条消息，避免摘要完全替代历史

总体来看，压缩中间件在长对话场景下是正收益的（成本降低、稳定性提升），但短对话场景可能不需要压缩。

```python
async def adaptive_threshold(state: AgentState) -> int:
    """根据对话类型动态调整阈值"""
    complexity = analyze_complexity(state.messages)

    if complexity == "high":  # 复杂任务，保留更多上下文
        return 120_000
    elif complexity == "low":  # 简单对话，更早压缩
        return 80_000
    else:
        return 100_000  # 默认阈值
```

## 指标说明（设计预期 vs 实测）

> 本节对上文「核心指标 / 量化成果建议」逐项标注来源属性：**实测**＝可从源码/可复现测试确认；**估算**＝基于设计推算、注明口径；**设计目标**＝期望达到但尚未实测。

| 指标 | 原表述 | 新属性 | 口径 / 复现方法 |
|------|--------|--------|----------------|
| 压缩率 70-85% | 70-85% | 估算 | 口径：压缩后 token / 原始 token。复现：用 `count_tokens_approximately` 比较压缩前后，对多轮对话取分布；当前无该脚本，属设计预期 |
| Token 误差 ±10% | ±10% | 实测（库特性） | `langchain_core.messages.utils.count_tokens_approximately` 的已知近似误差；非本项目在自有数据上标定，简历应写「近似计数，约 ±10%」而非「生产验证精度」 |
| 触发阈值 100K | 100K tokens | 实测 | `agents/context.py:12 DEFAULT_SUMMARY_THRESHOLD_K = 100` |
| 保留消息 10 | 10 条 | 实测 | `agents/context.py:13 DEFAULT_SUMMARY_KEEP_MESSAGES = 10` |
| 成本降低 60-75% | 60-75% | 估算 | 口径：长对话下压缩省下的 token 成本比。需结合真实账单核算，当前为设计预期 |
| 处理延迟 <2s | <2s | 估算 | 口径：一次摘要 LLM 调用耗时；文档自述 1-3s，取决于所选摘要模型 |

**如何复现这些数字（方法论）：**

1. **结构类（阈值/保留数）**：静态读 `agents/context.py` 即可确认。
2. **压缩率 / 成本降低**：构造多轮长对话（≥30 轮、含大量工具输出），触发压缩，用 `count_tokens_approximately` 算前后 token 比与成本差；对 N 个会话取分布，替换「70-85% / 60-75%」为实测。
3. **Token 误差**：取自有语料（中英混合、含代码），对比 `count_tokens_approximately` 与模型真实计费 token，算出实际偏差，校准「±10%」表述。

## 权衡与失效模式（Tradeoffs & Failure Modes）

**(a) 为什么选该技术方案而非主流替代**

- **结构化摘要压缩 vs 滑窗截断 vs 全量保留 vs 历史向量检索**：全量保留会在 128K 窗口触顶报错；滑窗截断直接丢失长期依赖；历史向量检索优雅但增加检索延迟与复杂度。选**结构化摘要**因成本低（一次 LLM 调用）、可控、信息保留维度清晰。
- **近似 token 计数 vs 精确 tiktoken**：`count_tokens_approximately` 无需加载分词器、实时零成本，±10% 足够触发阈值判断；tiktoken 精确但需与模型分词器对齐、有初始化开销。选近似因压缩触发是高频路径，精度够用。

**(b) 该设计在哪些场景会失效 / 踩坑**

- **摘要信息损失**：结构化 Prompt 强制保留 SESSION INTENT / REQUIREMENTS / PROGRESS / ARTIFACTS / NEXT STEPS，但若关键信息未落在这几类（如某个临时数字、一段长工具输出），可能被丢；长工具输出被截断到 `summary_tool_result_token_limit=500` 预览，关键结果可能只在「完整输出落盘路径」里。
- **压缩触发本身的延迟与成本**：每次压缩多一次 LLM 调用（文档自述 1-3s），短对话不划算；若对话整体短于阈值，压缩纯属浪费。
- **阈值余量偏小**：默认 100K 触发，但模型窗口 128K，叠加 system prompt / 工具 schema 后仍可能触顶；阈值未随模型动态变化。
- **摘要递归衰减**：反复压缩「已压缩历史」可能形成「摘要的摘要」，信息逐层衰减，文档未明确防止。
- **近似计数误差**：±10% 会让阈值判断提前/延后，极端下在临界附近抖动。

**(c) 当时如何兜底 / 缓解**

- 结构化 Prompt 强制保留 5 类关键信息；保留最近 `keep_messages=10` 条**不压缩**，避免摘要完全替代近期上下文。
- 工具结果清洗：完整输出落盘、消息仅留路径 + 预览，平衡信息完整与上下文占用。
- 阈值 / 保留数 / 摘要 Prompt 均为 `admin` 权限可配（`filter_config_by_role`），可按模型与场景调。
- 摘要由 LangGraph 内置中间件按 `summary_threshold` 自动执行，无需手写触发逻辑。

### 已知局限 / 如果重来

1. **压缩率 / 成本降低缺实测**：应建「压缩前后下游任务质量」评测，把 70-85% / 60-75% 从设计预期变实测；否则面试须标注估算。
2. **长工具输出截断到 500 token 可能丢关键结果**：若重来，应对关键字段（如测试结果、报错栈）设白名单强制保留摘要。
3. **100K 阈值余量不足**：应按模型上下文窗口动态算安全阈值（如 `window*0.8 - system_prompt`），而非写死 100K。
