# 10 - 用户认证与权限体系

StarRing 构建了一套完整的用户认证与权限控制体系，覆盖 JWT Token 认证、API Key 认证、OIDC 单点登录、基于角色的访问控制（RBAC）、部门级数据隔离和知识库级权限控制。

---

## 1. 认证机制

### 1.1 JWT Token 认证流程

StarRing 使用 **HS256 算法**签发 JWT，核心流程如下：

```
客户端 → 携带 Bearer Token → auth_middleware.get_current_user()
  → AuthUtils.verify_access_token(token)  # 解码并校验 exp/iss/aud/sub
  → 查询 User 表，校验 is_deleted / is_login_locked()
  → 返回 User 对象或抛出 401/423
```

**JWT Token 结构**：

| 字段 | 说明 |
|------|------|
| `sub` | 用户 ID（`str(user.id)`） |
| `exp` | 过期时间（默认 7 天） |
| `iss` | 签发者（`starring-know:{instance_id}`） |
| `aud` | 受众（`starring-know-api`） |

**安全设计**：
- 生产环境强制要求通过 `JWT_SECRET_KEY` 环境变量配置随机密钥，禁止使用公开默认密钥
- 开发环境未配置时自动生成临时随机密钥（服务重启后失效）
- Token 解码时**强制校验** `exp`、`sub`、`iss`、`aud` 四个声明
- 支持 `STARRING_INSTANCE_ID` 区分多实例部署

### 1.2 登录/注册流程

#### 首次初始化（系统引导）

系统首次启动时通过 `/api/auth/check-first-run` 检测是否需要初始化，若需要则调用 `/api/auth/initialize` 创建超级管理员：

1. 检查 `is_first_run` → 仅允许初始化一次
2. 验证 uid 格式（字母/数字/下划线，3-20 字符）
3. 创建"默认部门"
4. 创建 `role=superadmin` 的初始用户
5. 签发 JWT Token 返回

#### 常规登录

`POST /api/auth/token`（OAuth2 密码模式）：

1. 支持通过 **uid** 或 **手机号** 登录（防止用户名枚举攻击，统一返回"登录标识或密码错误"）
2. 校验用户是否已删除（`is_deleted`）
3. 校验是否处于登录锁定状态（`is_login_locked()`）
4. 使用 **Argon2** 验证密码（`AuthUtils.verify_password`）
5. 登录成功 → 重置失败计数器 + 签发 Token
6. 登录失败 → 递增失败计数器 + 判断是否锁定（5 次失败锁定 300 秒）

#### OIDC 单点登录

支持通过环境变量配置 OIDC Provider（如 Keycloak、Casdoor 等），实现：

1. 前端调用 `/api/auth/oidc/login-url` 获取授权链接
2. 用户在 IdP 完成认证后回调 `/api/auth/oidc/callback`
3. 后端用授权码换 Token → 获取 UserInfo → 查找或自动创建用户
4. 生成一次性 login code 重定向到前端
5. 前端调用 `/api/auth/oidc/exchange-code` 交换完整登录数据

**OIDC 用户映射策略**：
- 标准 OIDC 模式：uid 格式为 `oidc:{sub}`，直接按 sub 查找
- 原始用户名模式（`OIDC_USE_RAW_USERNAME=true`）：uid 使用 IdP 原始用户名，通过绑定占位记录防止账号冒用

### 1.3 API Key 认证

除 JWT 外，系统同时支持 **API Key 认证**，适用于 CLI 工具和程序化调用：

- Key 格式：`yxkey_{random_hex(24)}`
- 存储方式：仅保存 SHA-256 哈希值（`key_hash`），原始密钥仅在创建时返回一次
- 认证逻辑：`get_current_user()` 根据 token 前缀 `yxkey_` 判断走 API Key 路径
- 支持 Key 绑定用户或部门，过期时间控制，启用/禁用开关

#### CLI 浏览器授权流程（类 GitHub Device Flow）

用于 CLI 工具无浏览器场景下的安全认证：

1. CLI 调用 `/api/auth/cli/sessions` 获取 `device_code` + `user_code`
2. CLI 引导用户在浏览器中访问授权页面
3. 用户在浏览器中调用 `/api/auth/cli/sessions/{user_code}/approve` 批准
4. CLI 轮询 `/api/auth/cli/sessions/token` 用 `device_code` 换取 API Key
5. 会话 10 分钟超时

### 1.4 Token 刷新机制

当前 JWT 有效期为 7 天（`JWT_EXPIRATION = 7 * 24 * 60 * 60`），过期后需重新登录。系统**未实现 Refresh Token 机制**，而是通过较长有效期 + 登录锁定保护来平衡安全性与用户体验。

### 1.5 API 鉴权中间件

核心鉴权链通过 FastAPI 的 `Depends` 依赖注入实现，形成逐层递进的权限校验：

```
get_current_user  →  User | None（可选认证，未登录返回 None）
  ↓
get_required_user →  User（必须登录 + 绑定部门，否则 401/400）
  ↓
get_admin_user    →  User（必须 admin/superadmin 角色，否则 403）
  ↓
get_superadmin_user → User（必须 superadmin 角色，否则 403）
```

## 2. 权限体系

### 2.1 角色定义

系统定义三级角色，严格层级递进：

| 角色 | 权限范围 | 创建者 | 数量约束 |
|------|----------|--------|----------|
| `superadmin` | 全系统：所有部门/用户/知识库/系统配置 | 系统初始化 | 建议唯一 |
| `admin` | 本部门：管理本部门用户和资源 | superadmin | 每部门至少 1 个 |
| `user` | 个人：访问被授权的资源 | admin/superadmin | 无限制 |

**角色约束**：
- 禁止通过 API 创建 `superadmin` 账户
- `admin` 只能创建 `user` 角色用户
- `admin` 不能修改/删除其他 `admin` 或 `superadmin`
- 不能删除部门唯一的 `admin`（保障部门始终有管理员）
- 不能降级 `superadmin` 账户

### 2.2 权限控制粒度

#### API 端点级权限

通过 FastAPI 依赖注入实现端点级鉴权，各路由文件的权限分布：

| 依赖注入 | 使用路由 | 典型端点 |
|----------|----------|----------|
| `get_required_user` | auth_router, chat_router | `/auth/me`, `/auth/profile`, 对话接口 |
| `get_admin_user` | auth_router, knowledge_router, dashboard_router, model_provider_router, skill_router, mcp_router, system_router, system_task_router, tool_router, graph_router, knowledge_eval_router, auth_dept_router | 知识库管理、模型配置、系统设置、仪表盘 |
| `get_superadmin_user` | auth_router, auth_dept_router | `/auth/impersonate/{user_id}`, 部门增删改、用户部门变更 |

#### 部门级数据隔离

系统通过 `department_id` 实现部门维度的数据隔离：

- **用户管理隔离**：`admin` 只能看到和管理本部门用户；`superadmin` 可跨部门操作
- **部门管理员保护**：不能删除/降级部门唯一的 `admin`，不能将部门唯一 `admin` 调往其他部门
- **部门创建**：仅 `superadmin` 可创建部门，创建时需同时指定部门管理员
- **部门删除**：删除部门时，其下用户自动迁移至默认部门（ID=1），关联 API Key 同步清理
- **用户部门变更**：仅 `superadmin` 可修改用户的 `department_id`

#### Agent 上下文权限过滤

Agent 配置参数通过 `metadata.auth` 标记访问级别，`filter_config_by_role()` 在运行时按用户角色过滤：

代码实现（backend/package/starring/agents/context.py:50-57）：

```python
def _role_can_access(auth: str | None, role: str | None) -> bool:
    if not auth:           # 无标记 → 公开
        return True
    if auth == "admin":    # admin 标记 → admin + superadmin 可用
        return role in {"admin", "superadmin"}
    if auth == "superadmin":  # superadmin 标记 → 仅 superadmin 可用
        return role == "superadmin"
    return False
```

标记为 `auth="admin"` 的配置字段（如上下文压缩阈值、调试参数等）对普通用户不可见。

### 2.3 知识库级别的权限隔离

知识库通过 `share_config` 实现三级访问控制：

代码实现（backend/package/starring/knowledge/manager.py）：

```python
DEFAULT_SHARE_CONFIG = {
    "access_level": "global",
    "department_ids": [],
    "user_uids": []
}
```

| access_level | 访问规则 | 典型场景 |
|--------------|----------|----------|
| `global` | 所有登录用户可访问 | 公共知识库 |
| `department` | 指定部门列表中的用户可访问 | 部门内部知识库 |
| `user` | 指定 uid 列表中的用户可访问 | 私有知识库 |

**判断逻辑**（`_database_info_accessible`）：
1. `superadmin` 始终有权访问所有知识库
2. 知识库创建者始终有权访问自己创建的知识库
3. 按 `access_level` 判断：`global` → 放行；`department` → 校验部门归属；`user` → 校验 uid 列表
4. 列出知识库时，仅返回用户有权访问的知识库

### 2.4 API 端点的权限要求汇总

| API 分组 | 最低权限 | 关键端点 |
|----------|----------|----------|
| 认证/登录 | 无（公开） | `POST /auth/token`, `POST /auth/initialize`, OIDC 端点 |
| 个人信息 | `required_user` | `GET /auth/me`, `PUT /auth/profile`, `POST /auth/upload-avatar` |
| 对话/聊天 | `required_user` | `POST /chat/threads`, 对话流式接口 |
| 用户管理 | `admin` | `POST /auth/users`, `GET /auth/users`, `PUT /auth/users/{id}`, `DELETE /auth/users/{id}` |
| 知识库 | `admin` | 知识库 CRUD、文档上传/解析/检索 |
| 系统配置 | `admin` | `GET /system/config`, 系统日志 |
| 模型配置 | `admin` | 模型 Provider 增删改查 |
| 部门管理 | `superadmin` | 部门增删改（列表 `admin` 可查） |
| 模拟登录 | `superadmin` | `POST /auth/impersonate/{user_id}` |
| CLI 授权 | `required_user` | CLI Session 创建/审批 |

### 3.2 核心代码示例

#### JWT Token 签发与验证

```python
# backend/package/starring/utils/auth_utils.py

class AuthUtils:
    @staticmethod
    def create_access_token(data: dict, expires_delta: timedelta | None = None) -> str:
        to_encode = data.copy()
        expire = utc_now() + (expires_delta or timedelta(seconds=JWT_EXPIRATION))
        to_encode.update({"exp": expire, "iss": _get_jwt_issuer(), "aud": JWT_AUDIENCE})
        return jwt.encode(to_encode, _get_jwt_secret_key(), algorithm=JWT_ALGORITHM)

    @staticmethod
    def verify_access_token(token: str) -> dict:
        try:
            return jwt.decode(
                token, _get_jwt_secret_key(), algorithms=[JWT_ALGORITHM],
                issuer=_get_jwt_issuer(), audience=JWT_AUDIENCE,
                options={"require": ["exp", "sub", "iss", "aud"]},
            )
        except jwt.ExpiredSignatureError:
            raise ValueError("令牌已过期")
        except jwt.InvalidTokenError:
            raise ValueError("无效的令牌")
```

#### 鉴权依赖注入链

```python
# backend/server/utils/auth_middleware.py

async def get_current_user(authorization: str | None = Header(None), db=Depends(get_db)):
    """双模式认证：JWT Token 或 API Key（yxkey_ 前缀）"""
    token = authorization.split("Bearer ")[1]
    if token.startswith("yxkey_"):
        user, api_key_obj = await _verify_api_key(token, db)
        return user
    payload = AuthUtils.verify_access_token(token)
    user_id = payload.get("sub")
    user = await db.execute(select(User).filter(User.id == int(user_id), User.is_deleted == 0))
    return user.scalar_one_or_none()

async def get_required_user(user: User | None = Depends(get_current_user)):
    if user is None:
        raise HTTPException(401, detail="请登录后再访问")
    if not user.department_id:
        raise HTTPException(400, detail="当前用户未绑定部门")
    return user

async def get_admin_user(current_user: User = Depends(get_required_user)):
    if current_user.role not in ["admin", "superadmin"]:
        raise HTTPException(403, detail="需要管理员权限")
    return current_user

async def get_superadmin_user(current_user: User = Depends(get_required_user)):
    if current_user.role != "superadmin":
        raise HTTPException(403, detail="需要超级管理员权限")
    return current_user
```

#### 知识库权限判断

```python
# backend/package/starring/knowledge/manager.py

@staticmethod
def _database_info_accessible(user: dict, db_info: dict) -> bool:
    if user.get("role") == "superadmin":
        return True
    if db_info.get("created_by") == user.get("uid"):
        return True
    share_config = db_info.get("share_config") or DEFAULT_SHARE_CONFIG.copy()
    access_level = share_config.get("access_level")
    if access_level == "global":
        return True
    if access_level == "department":
        department_ids = [int(d) for d in share_config.get("department_ids") or []]
        return int(user.get("department_id")) in department_ids
    if access_level == "user":
        return user.get("uid") in (share_config.get("user_uids") or [])
    return False
```

#### 用户模型（含登录锁定）

```python
# backend/package/starring/storage/postgres/models_business.py

class User(Base):
    __tablename__ = "users"
    id = Column(Integer, primary_key=True)
    uid = Column(String, unique=True, index=True)        # 登录标识
    role = Column(String, default="user")                 # superadmin / admin / user
    department_id = Column(Integer, ForeignKey("departments.id"))
    login_failed_count = Column(Integer, default=0)       # 失败次数
    login_locked_until = Column(DateTime, nullable=True)   # 锁定截止时间
    is_deleted = Column(Integer, default=0, index=True)    # 软删除标记

    def is_login_locked(self) -> bool:
        return self.login_locked_until and utc_now_naive() < self.login_locked_until

    def increment_failed_login(self):
        self.login_failed_count += 1
        self.last_failed_login = utc_now_naive()
        if self.login_failed_count >= 5:  # MAX_LOGIN_FAILED_ATTEMPTS
            self.login_locked_until = self.last_failed_login + timedelta(seconds=300)
```

## 4. 简历写法建议

### 4.1 如何在简历中描述认证体系

> **项目**：StarRing 智能知识库平台
>
> **认证与权限体系**：
> - 基于 FastAPI 依赖注入设计四级鉴权链（匿名 → 登录用户 → 管理员 → 超级管理员），通过 `Depends` 逐层递进校验，覆盖全部 20+ 路由模块的 248 个端点
> - 实现 JWT（HS256）+ API Key 双模式认证，支持浏览器端 JWT Token 和 CLI 端 API Key 两种接入方式；API Key 仅存储 SHA-256 哈希，原始密钥仅在创建时返回
> - 设计三级 RBAC 角色体系（superadmin / admin / user）+ 部门级数据隔离，管理员仅可管理本部门用户和资源，超级管理员跨部门操作
> - 实现知识库三级访问控制（global / department / user），通过 `share_config` 字段在查询时按用户角色和部门归属动态过滤，superadmin 拥有全局访问权限
> - 集成 OIDC 单点登录，支持 Discovery 自动配置、自动创建用户、部门信息映射、账号绑定防冒用；实现 GitHub Device Flow 风格的 CLI 安全授权
> - 实现登录安全防护：Argon2 密码哈希、5 次失败锁定 300 秒、防止用户名枚举攻击、软删除 + 敏感信息清理、超级管理员模拟登录审计

### 4.2 面试高频问题

1. **JWT 和 Session 的区别？你为什么选择 JWT？**
   - JWT 无状态，不需要服务端存储会话，适合分布式部署和 API 认证场景；本项目为纯 API 后端，JWT 天然适配。缺点是难以主动撤销（可通过黑名单或短有效期 + Refresh Token 缓解）。

2. **API Key 存储为什么只存哈希？**
   - 参照业界最佳实践（GitHub Personal Access Token、AWS Access Key），即使数据库泄露也无法还原原始密钥，将影响限制在已泄露的单条记录。查询时对传入 key 做同样哈希后比对。

3. **如何防止用户名枚举攻击？**
   - 登录失败时统一返回"登录标识或密码错误"，不区分"用户不存在"和"密码错误"，避免攻击者通过不同错误信息判断用户是否注册。

4. **部门隔离怎么实现的？有哪些边界情况？**
   - 通过 `department_id` 外键关联，管理员查询/操作时自动过滤本部门数据。边界保护：不能删除部门唯一管理员、不能将唯一管理员调离、删除部门时用户迁移至默认部门。

5. **OIDC 登录中如何防止账号冒用？**
   - 使用 `oidc:{sub}` 格式的 uid 确保每个 IdP sub 唯一映射到一个系统用户；在 `use_raw_username` 模式下创建绑定占位记录（标记为 deleted），查询时解析绑定关系验证身份，防止不同 IdP 账号冒用同一系统账户。

6. **FastAPI 依赖注入鉴权链有什么优势？**
   - 声明式权限声明，代码可读性高；自动生成 OpenAPI 文档中的安全要求；依赖可组合复用（`get_admin_user` 内嵌 `get_required_user` 内嵌 `get_current_user`）；天然支持中间件模式扩展。

7. **知识库权限的 access_level 三级设计如何平衡安全与灵活？**
   - `global` 满足公共资源开放需求；`department` 适配企业组织架构隔离；`user` 支持细粒度个人授权。三级递进，从粗到细，覆盖从公开到私有的完整场景。权限判断在查询时动态执行，无需预计算权限表。
