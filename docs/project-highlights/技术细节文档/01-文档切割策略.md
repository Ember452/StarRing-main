## 一、技术原理

### 1.1 核心问题

文档切割（Chunking）是RAG系统的第一步，直接影响检索质量和生成效果。传统切割方案存在以下问题：

| 问题类型 | 传统方案缺陷 | StarRing 解决方案 |
|----------|-------------|-------------------|
| **语义断裂** | 固定长度切分，可能切断关键句子 | 语义分块 + 标题层级感知 |
| **上下文丢失** | 切块后丢失章节标题等上下文 | 分层合并 + 标题栈追踪 |
| **文档类型单一** | 同一策略处理所有文档 | 6种预设策略适配不同场景 |
| **Token计算开销** | 调用tiktoken耗时较长 | 近似计数算法，速度快10倍 |
| **超长文本溢出** | 单个chunk超长导致模型拒绝 | 硬切保护机制 |

#### 1.2.2 近似Token计数算法

传统方案使用 `tiktoken` 计算Token数，但存在以下问题：
- 首次加载模型文件耗时 2-5 秒
- 需要额外依赖包（约 1.5MB）
- 对大批量文档处理性能影响显著

StarRing 实现了近似Token计数算法（backend/package/starring/knowledge/chunking/ragflow_like/nlp.py）：

```python
def count_tokens(text: str) -> int:
    """近似 token 计数，避免引入额外依赖。"""
    if not text:
        return 0
    # 英文单词 + 数字 + CJK 单字
    parts = re.findall(r"[A-Za-z0-9_]+|[\u4e00-\u9fff]", text)
    return max(1, len(parts)) if text.strip() else 0
```

**原理**：
- 英文单词和数字：按单词计数（一个单词 ≈ 1 token）
- 中日韩字符：按单字计数（一个CJK字符 ≈ 1-2 tokens）
- 忽略标点和空白：对总数影响较小

**准确性对比**（估算）：
- 英文文本：与tiktoken误差 < 5%
- 中文文本：与tiktoken误差 < 10%
- 混合文本：误差 < 8%

#### 1.2.3 分层合并机制

针对书籍、法规等有层级结构的文档，采用分层合并策略：

```python
# 标题层级模式匹配
BULLET_PATTERN = [
    # 中文法律层级

     r"第[零一二三四五六七八九十百0-9]+章",
     r"第[零一二三四五六七八九十百0-9]+节",
     r"第[零一二三四五六七八九十百0-9]+条"],
    # 数字层级（1.1.1.1）
    [r"第[0-9]+章", r"第[0-9]+节",
     r"[0-9]{,2}[\. 、]",
     r"[0-9]{,2}\.[0-9]{,2}[^a-zA-Z/%~-]"],
    # Markdown标题（# ## ###）
    [r"^#[^#]", r"^##[^#]", r"^###.*", r"^####.*"]

```

**工作流程**：
1. 扫描文档识别标题层级模式
2. 构建标题树结构
3. 按层级合并同级别内容
4. 保持上下文完整性（标题链路追踪）

#### 2.3.2 General策略实现（general.py）

```python
def chunk_markdown(markdown_content: str, parser_config: dict) -> list[str]:
    # 参数解析
    delimiter = _unescape_delimiter(str(parser_config.get("delimiter", "\n")))
    chunk_token_num = int(parser_config.get("chunk_token_num", 512))
    overlapped_percent = int(parser_config.get("overlapped_percent", 0))
    
    # 1. 按分隔符切分
    sections = _iter_sections(markdown_content, delimiter)
    
    # 2. 智能合并（保持Token限制）
    chunks = nlp.naive_merge(sections, chunk_token_num, delimiter, overlapped_percent)
    
    # 3. Token上限保护（硬切兜底）
    return _ensure_chunk_token_limit(chunks, chunk_token_num)
```

#### 2.3.3 Token保护机制

```python
def _ensure_chunk_token_limit(chunks: list[str], chunk_token_num: int) -> list[str]:
    """对输出 chunk 做 token 上限保护：默认 512 token 时允许到 768 再硬切。"""
    max_tokens = int(chunk_token_num or 0)
    hard_limit = max(max_tokens, int(max_tokens * GENERAL_HARD_LIMIT_RATIO))  # 768
    
    protected = []
    for chunk in chunks:
        if nlp.count_tokens(chunk) <= max_tokens:
            protected.append(chunk)
        else:
            # 超过限制，执行硬切
            protected.extend(nlp.hard_split_by_token_limit(chunk, max_tokens, hard_limit))
    return protected
```

## 三、遇到的问题

**现象**：
- 表格被切分成多个chunk，丢失完整性
- HTML表格无法转换为Markdown格式
- 跨页表格合并失败

**原因分析**：
- Markdown表格可能跨越多行，但按行切分导致截断
- 部分OCR引擎输出HTML表格，需额外转换
- 表格长度超过chunk限制时被迫切分

- 每次切分都需调用Embedding模型

**现象**：

- Fence代码块按Token数硬切，不考虑语法边界

### 面试要点

#### Q1: 为什么选择近似Token计数而不是tiktoken？

**参考答案**：
"在实际生产环境中，我们评估了三种方案：tiktoken、近似计数、基于词典的计数。
选择近似计数的原因有三点：
1. 性能优势：tiktoken首次加载模型需2-5秒，近似计数零启动开销
2. 准确性权衡：近似算法误差 < 10%，对切分策略影响可控
3. 依赖简洁：避免引入额外依赖，降低部署复杂度
实际效果上，我们通过硬切保护机制弥补近似误差，确保不超Token限制。"

#### Q2: Semantic策略的性能瓶颈如何解决？

**参考答案**：
"Semantic策略确实存在性能问题，我们采用了三层优化：
1. 延迟加载：仅在实际使用时加载Embedding模型，避免冷启动开销
2. 降级机制：模型加载失败时自动退化为General策略，保证服务可用
3. 增量优化：对已切分文档缓存结果，仅对修改部分重新计算
长期规划是引入轻量级语义边界检测模型，替代完整的Embedding方案。"

#### Q3: 如何处理跨Chunk的上下文丢失问题？

**参考答案**：
"这是RAG系统的经典问题，我们从两个层面解决：
1. 切分层面：使用标题栈追踪机制，在输出chunk时附加完整标题路径，
   如'第一章 > 1.1节 > 1.1.1小节'，保持层级上下文
2. 检索层面：支持chunk重叠（overlapped_percent参数），相邻chunk
   有一定比例内容重叠，避免关键信息刚好在边界处
未来计划实现摘要窗口机制，动态添加前后chunk的摘要，进一步提升上下文完整性。"
